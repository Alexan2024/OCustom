# ÖMANKÖ custom station

Telegram-бот и мини-апп: покупатель собирает футболку из готовых DTF-принтов
(в реальном масштабе), сотрудник получает спеку в миллиметрах и запечатывает.
Забрать можно самому в поп-апе или заказать доставку СДЭК.

**Запуск описан в файле `ИНСТРУКЦИЯ.md` — открывай его, а не этот файл.**

Техническая справка:

```
run.py            запуск (веб + бот + фоновые задачи одним процессом)
app/config.py     цены, размеры, печатные зоны, доставка — из переменных окружения
app/db.py         SQLite, резерв остатков, автоимпорт stickers/stickers.csv
app/api.py        API мини-аппа + валидация геометрии + вебхуки ЮKassa и СДЭК
app/bot.py        /start, /terms, /chatid, карточки заказов, статусы, накладные
app/payments.py   ЮKassa (API v3): создание платежа, проверка статуса, чек
app/cdek.py       СДЭК (API v2): города, ПВЗ, тариф, накладная, трек-номер
app/jobs.py       автоотмена неоплаченных заказов + доопрос накладных СДЭК
app/render.py     картинка раскладки заказа (карточка «Мои заказы» в боте)
app/auth.py       проверка подписи Telegram initData
webapp/           мини-апп, без сборки (HTML + CSS + JS)
stickers/         картинки принтов + stickers.csv (каталог)
```

## Мини-апп

Светлая тема, серый акцент. Разметку (пунктир зоны, мм-сетку, подписи)
можно спрятать кнопкой «Как выглядит» — покупатель смотрит на футболку,
а не на чертёж.

Поворот принта свободный, 0..359°: угол ⟲ на выделенном принте или два
пальца по нему. Магнит подтягивает угол к 0/90/180/270 в пределах 5°.
Габарит, которым принт удерживается в зоне, всегда неповёрнутый — значит
на промежуточных углах углы принта выходят за пунктир. Это допущено
сознательно, и мини-апп с сервером считают это одинаково
(`validate_geometry` в `app/api.py`).

Количества покупателю не показываем. Разобранный принт остаётся в каталоге
бледным, со штампом SOLD OUT: `/api/stickers` отдаёт и нулевые остатки,
а мини-апп раз в 45 секунд переспрашивает каталог — если принт разобрали,
пока человек собирал футболку, он увидит это сразу, а не при оформлении.

Дневная квота заказов по умолчанию выключена (`ONLINE_QUOTA_PER_DAY=0`).

## Остаток бланков

Живёт в таблице `shirt_stock`, а не в переменной окружения: `SHIRT_STOCK`
теперь только стартовое значение и подставляется размеру, которого ещё нет
в базе. Правится командой `/stock` из чата сотрудников — панель с кнопками
±1/±5 на каждый размер, точное число `/stock M 20`, прибавить `/stock M +5`.
Считает база (`add_shirt_stock` в одной транзакции): по кнопкам в общей
группе жмут вдвоём.

Заказ резервирует бланк тем же способом, что и принты — внутри транзакции
`create_order`, отмена возвращает его через `_restock`. Проверка остатка
есть и снаружи, в `api.py`, но решает внутренняя: между внешней проверкой
и записью заказа помещается чужой заказ на последнюю футболку. Ноль скрывает
размер в мини-аппе; про ноль и про `SHIRT_STOCK_LOW` бот пишет в чат
сотрудников сам. `SHIRT_STOCK_AUTO=false` — списание выключено, число
остаётся просто заслонкой.

## Мои заказы

`/orders` в боте (и кнопка в меню команд) присылает по карточке на каждый
активный заказ: картинка раскладки, номер, статус, сумма, куда едет,
трек-номер. Картинку рисует `app/render.py` теми же формулами, что и
мини-апп. Выданные и отменённые заказы в список не попадают.

## Оплата

`PAYMENT_MODE=manual` — сотрудник подтверждает оплату кнопкой.
`PAYMENT_MODE=yookassa` — платёж создаётся по API, ссылка уходит покупателю
в чат, факт оплаты ловится вебхуком на `/api/payments/yookassa/webhook`.

Тело вебхука доказательством не считается: из него берётся только id платежа,
после чего сервер сам запрашивает `GET /v3/payments/{id}` и сверяет статус
и сумму. Плюс два запасных пути на случай потерянного уведомления —
проверка при возврате человека в бота (`/start paid_N`) и фоновая проверка
перед автоотменой.

Чек по 54-ФЗ собирается только при `YOOKASSA_SEND_RECEIPT=true`. Доставка
идёт в чеке отдельной строкой как услуга — иначе сумма позиций не сойдётся
с суммой платежа и ЮKassa откажет.

Контакт покупателя в чеке — **электронная почта**, её спрашивают на экране
оформления. Одного телефона мало: по нему чек доставляется SMS-кой, а SMS
у ОФД по умолчанию выключены — в налоговую чек уходит, покупатель не получает
ничего. Телефон кладётся в чек дополнительно, когда он есть (заказы
с доставкой). Адрес запоминается в `customers.email` и подставляется
в следующий раз.

## Условия возврата

Футболка по индивидуальному макету возврату и обмену без брака не подлежит
(ст. 26.1 ЗоЗПП, п. 4 ст. 497 ГК). Покупатель подтверждает это галочкой
на экране оформления **до оплаты**; момент согласия пишется
в `orders.terms_accepted_at`. Заказ без галочки сервер не принимает.
Полный текст лежит в `RETURN_POLICY_TEXT` (строка у галочки —
`RETURN_POLICY_SHORT`), доступен по `/terms` и по кнопке под `/start`.

## Доставка

Самовывоз есть всегда. СДЭК включается флагом `DELIVERY_CDEK=true`; пока он
выключен, мини-апп показывает один способ получения и ни одного запроса
в СДЭК не уходит.

Схема отправки одна: сотрудник относит пакет в свой ПВЗ
(`CDEK_SHIPMENT_POINT`), дальше СДЭК везёт его либо в ПВЗ получателя
(тариф 136), либо курьером до двери (тариф 137). Забор курьером от поп-апа
не используется — его надо заказывать заранее, а поп-ап работает не по
складскому расписанию.

Цена доставки фиксированная и одна на всю Россию: `CDEK_PRICE_PVZ` (400 ₽)
и `CDEK_PRICE_DOOR` (800 ₽). Направление на неё не влияет — где-то это дороже
реального тарифа, где-то дешевле, разница закрывается в среднем по заказам.
Калькулятор СДЭК всё равно опрашивается, но только ради срока доставки:
не ответил — покажем цену без срока, а не уроним оформление. Обе переменные
в `0` возвращают старое поведение, расчёт по тарифу плюс
`DELIVERY_MARKUP_RUB`.

Цену доставки мини-апп только показывает. При создании заказа сервер
проставляет её заново сам и пишет в базу свой результат: подменить сумму
из клиента нельзя. Адрес ПВЗ тоже берётся из ответа СДЭК, а не из мини-аппа —
в карточке сотрудника должно лежать то, что реально уедет в накладную.

Накладная создаётся сразу после оплаты (`CDEK_CREATE_ON_PAID=true`,
по умолчанию): трек-номер уходит покупателю через минуту, ещё до печати.
Сообщение при этом честное — «отслеживание оживёт, когда передадим посылку
в СДЭК», иначе пустой трекинг через день читается как потерянная посылка.
Отмена заказа гасит накладную через `DELETE /v2/orders/{uuid}`; если СДЭК
удалить не даёт (пакет уже приняли), бот зовёт сотрудника. С флагом `false`
накладная, как раньше, создаётся при переводе заказа в «Готово».

Если СДЭК не ответил, в карточке остаётся кнопка «Создать накладную СДЭК ↻».

Статусы приходят вебхуком на `/api/delivery/cdek/webhook`. Доверия к телу
уведомления столько же, сколько к оплате: берём из него uuid и сами
спрашиваем `GET /v2/orders/{uuid}`. Раз в десять минут активные отправления
доопрашиваются фоном — на случай потерянного уведомления. Статус
`DELIVERED` сам закрывает заказ; `NOT_DELIVERED` и возврат зовут сотрудника.

Приёмка пакета в СДЭК сама переводит заказ в «Передан в СДЭК»
(`CDEK_AUTO_SHIPPED=true`, по умолчанию): карточка в чате сотрудников
перерисовывается, покупателю уходит «заказ уехал» с трек-ссылкой. Кнопка
«Сдал в СДЭК 🚚» остаётся, но перестаёт быть обязательной — сотрудник сдаёт
пакет в ПВЗ и уходит, а не вспоминает про телефон. Признаком считается любой
статус приёмки в истории накладной, а не только последний: между двумя
опросами посылка успевает проскочить несколько состояний. «Накладная создана»
приёмкой не считается — она заводится сразу после оплаты, когда футболку
ещё печатают.

`CDEK_TEST=true` — песочница `api.edu.cdek.ru`, реквизиты подставляются
сами, договор не нужен. Заказы в ней настоящей посылкой не становятся.

Локально: `pip install -r requirements.txt`, задать `BOT_TOKEN` и `WEBAPP_URL`
(HTTPS-туннель, например `cloudflared tunnel --url http://localhost:8080`),
затем `python run.py`.
